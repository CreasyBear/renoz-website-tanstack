# GEO/SEO Remediation Plan

Generated by `/plan-eng-review` on 2026-04-28.

Branch: main
Base commit observed: a1705de

## Goal

Fix the GEO/SEO audit gaps for `renoz-website-tanstack` without changing the site's product positioning or visual design. The work should make the site easier for Google, AI search engines, and assistant crawlers to understand, cite, and trust.

## Source Inputs

- GEO/SEO audit based on the `geo-seo-claude` framework.
- Existing TanStack Start route/head setup.
- Existing `public/robots.txt`, `public/llms.txt`, `public/sitemap.xml`, and route-level metadata.
- Google Search Central canonical/sitemap guidance.
- TanStack Router document head guidance.
- Schema.org `BreadcrumbList`, `Product`, `FAQPage`, `WebPage`, and organization/local business patterns.

## What Already Exists

- Root document head and entity schema in `src/routes/__root.tsx`.
- Route-level title/description/OG metadata on most static pages.
- Static sitemap in `public/sitemap.xml`.
- Dynamic sitemap handler in `src/routes/sitemap.xml.tsx`, currently mounted at `/sitemap/xml`.
- Strong `llms.txt` briefing in `public/llms.txt`.
- Shared SEO helpers in `src/lib/seo.ts`, including `generateSitemap` and `generateBreadcrumbs`.
- FAQ content in `src/components/sections/FAQ.tsx` and `src/routes/contact.tsx`.
- Case study data in `src/data/case-studies.ts`.
- Product facts spread across product pages, product index, capability statement, and `llms.txt`.

## Proposed Scope

### 1. Canonical and Head Consistency

Add a small SEO helper layer in `src/lib/seo.ts` for canonical URLs and JSON-LD generation.

Target helpers:

- `siteUrl(path: string): string`
- `canonicalLink(path: string)`
- `jsonLd(data: unknown)`
- `pageMeta({ title, description, path, image?, type? })`
- `breadcrumbSchema(pathname: string, labels?: Record<string, string>)`

Use these helpers in route `head` functions instead of hand-repeating URL construction.

### 2. Sitemap Source of Truth

Make the sitemap route and static sitemap agree.

Preferred implementation:

- Move the dynamic route to serve `/sitemap.xml` if TanStack file routing supports the literal route cleanly.
- If file routing cannot expose `/sitemap.xml` safely, keep static `public/sitemap.xml` but generate it from one shared route list.
- Remove `/installers`.
- Add `/partners` and `/partners/capability-statement`.
- Include all public static routes and known case studies.
- Add `lastmod`, `changefreq`, and `priority` consistently.

### 3. Case Study Metadata and Schema

Add dynamic head metadata in `src/routes/case-studies/$slug.tsx`.

Each case study detail page should emit:

- Title: `{study.title} | RENOZ Energy Case Study`
- Description from `study.summary`.
- Canonical URL.
- `og:title`, `og:description`, `og:image`, `og:url`, `og:type: article`.
- Twitter card metadata.
- `Article` or `CreativeWork` schema with location, date, image, description, and `about`.
- `BreadcrumbList` schema.

### 4. Product and FAQ Structured Data

Add Product schema to:

- `/products/residential`
- `/products/rural`
- `/products/commercial`

Add FAQPage schema to:

- Home page FAQ section.
- Contact page FAQ section.

Use one JSON-LD helper so this remains boring and explicit rather than copied by hand.

### 5. GEO Evidence Blocks

Move the strongest `llms.txt` claims into visible, crawlable page sections.

Initial evidence targets:

- About page: certifications, GreenTech Hub finalist, Brill Power partnership, team expertise.
- Case studies index/detail: measurable outcomes and media/context.
- Product pages: operating temperature, cycle life, warranty, compatibility, support model.
- Resources page: document evidence pack with clearer machine-readable descriptions.

Keep these blocks short and factual. The goal is not more marketing copy; the goal is corroboration for claims already made in `llms.txt`.

### 6. AI-Citable Answer Blocks

Add concise 120-180 word answer-style sections for high-intent questions:

- What is RENOZ Energy?
- Is RENOZ Australian-made?
- How much does a RENOZ battery cost?
- What warranty does RENOZ offer?
- Can RENOZ batteries work off-grid?
- How does RENOZ compare with Tesla Powerwall?

These can live on existing pages, with anchors linked from `llms.txt`.

### 7. Robots and AI Crawler Policy

Update `public/robots.txt` to explicitly include common AI/search crawlers where business policy is to allow crawling.

Candidate additions:

- PerplexityBot
- ClaudeBot
- Applebot
- Bingbot
- Googlebot
- OAI-SearchBot
- Meta-ExternalAgent

Keep `/admin`, private generated paths, JSON endpoints, and sensitive form/API routes blocked where appropriate.

### 8. Local Render Verification

Fix or isolate the local runtime-preview blockers observed during the audit:

- `npm run dev` starts but throws `ReferenceError: module is not defined` from `react/jsx-runtime.js`.
- Nitro preview via `npx srvx --static ../../static .vercel/output/functions/__server.func/index.mjs` fails with `EMFILE: too many open files, watch`.

This is needed so the final GEO/SEO QA can validate rendered HTML, not just source files.

## Data Flow

```text

        |
        v

  - canonical URL
  - meta helpers
  - JSON-LD helpers
  - sitemap entries
        |
        +------------------+
```

## Implementation Order

1. Add SEO helper functions and shared sitemap route list.
2. Fix sitemap route/static output mismatch.
3. Add canonical links to all indexable routes.
4. Add case-study dynamic metadata and schema.
5. Add Product, FAQPage, BreadcrumbList, and WebPage schema where useful.
6. Update visible evidence and AI-citable answer blocks.
7. Update `robots.txt` crawler policy and `llms.txt` links/last-updated.
8. Fix local render-preview blockers or document a verified workaround.
9. Run source-level, build-level, and rendered-page QA.

## Verification Commands

- `npm run build`
- `npm run test`

- JSON-LD parse check for every rendered page with schema.
- Sitemap route coverage check against `src/routeTree.gen.ts` or shared route list.

## Failure Modes

| Codepath | Failure Mode | Expected Handling |
|---|---|---|
| Canonical helper | Double slashes or trailing slash drift | Unit tests cover path normalization |
| Sitemap generator | Public route missing or stale deleted route included | Route coverage test fails |
| Case-study head | Unknown slug produces undefined metadata | Loader already throws `notFound`; test covers invalid slug |
| JSON-LD helper | Invalid JSON script emitted | Unit test parses all emitted schemas |
| Product schema | Marketing copy and schema facts drift | Product facts should come from shared constants where practical |
| FAQ schema | FAQ text diverges from visible FAQ | Generate schema from the same FAQ array |
| Robots policy | Accidentally blocks AI crawlers or sensitive routes | Snapshot/fixture test covers allow/block matrix |
| Render preview | Local server fails silently | QA requires successful rendered crawl before shipping |

## NOT In Scope

- Rewriting visual design or layout.
- Adding a blog/CMS.
- Building a search page just to satisfy existing WebSite `SearchAction`.
- Creating new product SKUs or changing product claims.
- Verifying external brand mentions across Reddit, Wikipedia, YouTube, or LinkedIn.
- Running live Google Rich Results tests in CI.
- Reworking forms, warranty flow, Supabase schema, or Turnstile behavior.

## Open Engineering Decisions

1. Whether to make `/sitemap.xml` dynamic or generate static `public/sitemap.xml` from shared data at build time.
2. Whether product facts should be centralized immediately or kept page-local for minimal diff.
3. Whether local render-preview blockers are in scope for the same PR or a prerequisite cleanup PR.
4. Whether to add rendered-head tests with the existing test stack or rely on browser QA plus helper unit tests.
